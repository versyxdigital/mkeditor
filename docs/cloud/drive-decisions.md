# Google Drive decisions

Recorded 23 November 2026. Scope: the [Drive ticket](cloud-provider-integration.md), with the [shared standards](cloud-provider-standards.md). Dropbox remains a separate roadmap ticket.

## A — OAuth and desktop scope

Default connections use `https://www.googleapis.com/auth/drive.readonly`. **Enable editing** explicitly requests fresh consent for read-only plus `https://www.googleapis.com/auth/drive`, and verifies the actual granted scopes before enabling writes. Failed/cancelled upgrades retain the original credential and access mode. Broad access supports browsing arbitrary existing folders; `drive.file` alone cannot provide that browser. Both broad scopes are restricted and require Google's public-app verification; a security assessment may apply. See [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) and the [submission guide](google-verification.md).

Registration is a **Desktop app** OAuth client. Use PKCE S256, an ephemeral IPv4 loopback listener bound only to `127.0.0.1`, and a three-minute sign-in deadline. The redirect is `http://127.0.0.1:<ephemeral-port>/oauth/callback`. Open consent in the system browser. The Desktop client secret is a public client value, not a confidential trust boundary. It is configurable alongside the client ID and is not logged. Tokens remain in main and are encrypted using Electron's OS-backed `safeStorage`; Linux `basic_text` and `unknown` backends are rejected.

MKEditor ships a shared public Desktop registration injected into `dist/app/config/googleDrive.json` at build time. The committed source template is empty; registration values come from build environment variables or an ignored local file. The release workflow requires the corresponding Actions secrets. Normal users only authorize their account; they do not register a Google app. Custom registration is optional under Advanced. Connections persist the registration used to authorize them so future build changes cannot silently switch an existing account's OAuth client. Google's publishing/verification remains a maintainer-side prerequisite for general public use.

**Correction to the proposal:** Google's [Desktop OAuth guide](https://developers.google.com/identity/protocols/oauth2/native-app) says incremental authorization is not supported for installed apps. A later permission change needs a fresh consent flow, not an assumed incremental upgrade. Normal account connections still request only read access. The separately authorized opt-in verifier requests `drive.file` alongside read access, solely for a marked disposable test file, using ephemeral credentials.

Google's [token expiration guidance](https://developers.google.com/identity/protocols/oauth2#expiration) says external apps in Testing generally receive refresh tokens expiring in seven days, with exceptions for basic profile scopes. Drive is not such an exception. Add your account as a test user and expect reauthorization during development.

Release targets from `package.json`: Windows NSIS, macOS PKG, Linux DEB. Development and offscreen desktop checks were performed on Windows only; no macOS/Linux runtime or installer verification is claimed.

## B — Existing-file save precondition

**Pass for ordinary Markdown blobs in My Drive using Drive v2 multipart updates.** Live verification completed on 23 November 2026 at 13:14:36 UTC against the owner's connected account, with temporary `drive.readonly` plus `drive.file` consent on a newly generated, marked disposable file. The file was trashed afterward. The exact verified write is `PUT https://www.googleapis.com/upload/drive/v2/files/{fileId}?uploadType=multipart&supportsAllDrives=true`, with `If-Match` set to the provider-issued v2 `File.etag` and a `multipart/related` body containing empty JSON metadata plus UTF-8 `text/markdown` media.

All three current-validator controls returned HTTP 200. All three stale-validator attempts returned HTTP 412. In every stale case, the independently changed bytes, MD5 checksum, blob `headRevisionId`, name, MIME type, parents, modified time and app properties remained unchanged. The schema-2 report is `out/drive-write-verification-v2-multipart.json`. Stage 1b may use **this endpoint and format for this item class**, with the existing account, permission, snapshot and recovery boundaries. Shared-drive writes and Google-native formats were not verified and remain read-only.

**Version-counter clarification:** earlier probes treated Drive's general `version` counter as the content revision and reported failure when it advanced despite a rejected write. Google's [File resource documentation](https://developers.google.com/workspace/drive/api/reference/rest/v2/files) defines that counter as including server changes not visible to the caller; it separately exposes the blob's `headRevisionId`. The refined verifier records both, requires unchanged actual content revision/checksum/bytes and visible metadata, and does not infer a content write solely from a bookkeeping-counter increment. Two successful final rejection cases advanced only the general counter; the third preserved it too. Fixtures cover both harmless counter advances and a rejected write that changes visible metadata (which still fails).

The paragraphs below record the investigation before that final result.

**Blocked pending a live conditional-write spike with an authorized disposable file.** On 23 November 2026, the owner reported successful Google app setup and the documented connection flow. That read-only test does not demonstrate a server-enforced write precondition, and no live write spike has been reported. Neither an ETag observed in fixtures nor a metadata version check provides that proof. The adapter therefore has **no update endpoint**, and Drive tabs are read-only. Save cannot route a remote identity into local filesystem IO. “Edit a local copy” creates a separate dirty untitled buffer for normal local Save As.

The owner subsequently authorized running this spike and continuing implementation. A real opt-in verifier now exists (`npm run verify-drive-writes`), with fixture checks for successful enforcement, ignored `If-Match`, absent validators, lost create responses and ownership-restricted cleanup. The first consent attempt stopped before the test. A second attempt completed Google consent and account verification on 23 November 2026, using separate in-memory tokens for `drive.readonly` plus `drive.file`; the existing saved connection was unchanged.

**Live v3 result: inconclusive, 23 November 2026 at 12:59:34 UTC.** The verifier generated an ID, created an ordinary Markdown file in My Drive, retrieved its full v3 metadata (`fields=*`) and media, then trashed the marked test file successfully. Neither retrieval supplied a provider-issued strong ETag. No current/stale update rounds were attempted, so this is not proof that v3 enforces or ignores `If-Match`. The candidate remained `PATCH https://www.googleapis.com/upload/drive/v3/files/{fileId}?uploadType=media&supportsAllDrives=true`, with `Content-Type: text/markdown; charset=utf-8` and `If-Match`. The non-secret run report is in `out/drive-write-verification.json`.

The [v2 File resource](https://developers.google.com/workspace/drive/api/reference/rest/v2/files) documents a file `etag`. A separate v2 spike is being checked using that value against the actual `PUT https://www.googleapis.com/upload/drive/v2/files/{fileId}?uploadType=media&supportsAllDrives=true` endpoint. Run it with `npm run verify-drive-writes -- --v2`; it uses the same narrow consent and ownership/cleanup safeguards and writes `out/drive-write-verification-v2.json`. The v2 endpoint must independently pass all current/stale controls; existence of its ETag field alone does not pass the gate. Shared-drive writes are not covered by a My Drive result.

Current official sources inspected: [v3 files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update), [upload documentation](https://developers.google.com/workspace/drive/api/guides/manage-uploads), and [performance guidance](https://developers.google.com/workspace/drive/api/guides/performance). Generic discussion of ETags in the performance guide does not establish atomic content-upload behavior on this endpoint. The verifier therefore requires successful current-validator controls, changed provider validators, HTTP 412 on stale attempts, and unchanged newer bytes/revisions across three rounds; missing strong validators or incomplete requests stay inconclusive.

Proposed spike endpoint for a later authorized disposable-account test: Drive API v3, `PATCH https://www.googleapis.com/upload/drive/v3/files/<id>?uploadType=media&supportsAllDrives=true`, `Content-Type: text/markdown`, `Authorization: Bearer <token>`, and `If-Match: <validator from the corresponding file resource>`. This is a candidate to investigate, **not a documented guarantee or an enabled save implementation**. Verify the actual validator source and upload semantics first.

Record the exact endpoint, API version, response headers/validator, OAuth scope, date and item type. A current-validator write must succeed. After an external change, the stale-validator write must be rejected and the external bytes must remain unchanged. Repeat at least three times on My Drive and separately for any shared-drive item type that would be enabled. Use only disposable contents; never print or commit tokens. If the server accepts a stale validator or the result is inconclusive, retain read-only behavior.

At that point Stage 1b and the cloud create/copy path were deferred until the live gate passed. The subsequent pass recorded above authorized their implementation. The current application retains read-only defaults, requires explicit fresh editing consent, and exposes no force-save bypass.
